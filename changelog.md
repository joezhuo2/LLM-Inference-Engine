# Changelog

Changes are grouped by branch, newest first, in the order the branches merge into `main`. Each entry is tagged with its part of the delegation: Part A and Part B entries are written by Claude and reviewed by Joe, and Part C entries are written by Joe.

## server/http

- Split the step object out of the trace writer as `step_json`, so the trace file and the server's live step stream (`GET /v1/steps`) write a step through the same function, byte for byte the same shape. (Part A)
- Add the `engine_server` library (`src/server/`, `include/engine/server/`) with the OpenAI-compatible chat API of `docs/api.md`: `parse_chat_request` reads `messages`, `max_tokens`, `temperature`, `top_p`, `top_k`, `seed`, `stop` (a string or a list) and `stream`, treats a null field as missing, falls back to the server defaults, and rejects anything else with an `ApiError` (status 400) whose message names the field; `resolve_max_tokens` clamps the default to the context left after the prompt and rejects an explicit `max_tokens` that does not fit; and the stream chunks (role, content, finish), the non-streamed `chat.completion` with `usage`, the error body and the SSE framing, with the `engine` extension (`seq_id`, `step`) on every chunk. (Part A)
- Add `CorsPolicy` (`src/server/cors.cpp`): exact-match allowed origins, `Access-Control-Allow-Origin` echoed only for them with `Vary: Origin`, and preflight headers (methods `GET, POST, OPTIONS`, the requested headers, a 600 s max age, and `Access-Control-Allow-Private-Network: true` when the browser asks with `Access-Control-Request-Private-Network: true`). An origin must be a bare `http://` or `https://` scheme and host, so `*`, paths and trailing slashes are rejected. The default list is only `http://localhost:3000`: the site's Vercel domain is not known yet and guessing one would let whoever owns that name call the local server. (Part A)

## web/kv-visualizer

- Add "allocate it yourself" to the paged KV story (issue #76), right above "how it works": a 64-block pool drawn as an isometric 3D grid on a canvas, each block a column whose height is the slots written and whose color is the request (L1, L2, L3 from `results/kv_demo.json`), with the empty rest of a held block drawn as a dashed outline. A TypeScript model of the BlockManager and scheduler rules (lowest free block, block 0 reserved, admit when the whole length fits, one slot per decode step, preempt the newest) serves the requests; a toggle replays the same arrivals with contiguous allocation, each request reserving its prompt plus 256 tokens first-fit, and a table compares both (blocks held, slots held but empty, requests waiting, preemptions). The built-in demo makes contiguous queue a request for 15 steps while paged uses a third of the blocks. Hovering a block, or focusing its entry in the block tables, shows its request and logical block, the tokens in its slots, and its K and V offsets and strides in the engine's 12,915-block pool. Request colors are three new validated series tokens for both themes. Plays when scrolled into view, not with reduced motion. (Part A)
- Add `scripts/kv_demo.py`, which answers three chat prompts from `scripts/prompts.json` (capital, haiku, kv_cache) greedily with `engine generate` and records each one token by token in `results/kv_demo.json` for the KV visualizer on the site. ## kernel/rope-vec-impl

- Fix `engine::fast::rope` (`src/kernels/rope_fast.cu`) so it is bit-identical to `naive::rope`: the first draft computed `inv_freq` on the device with `__powf`, which differs from the host `std::pow` in the last bit for some frequencies, and a one-ulp change in a rounded cosine or sine moves many outputs at large positions (3 of the 9 `FastRope` tests failed with a few mismatched elements each; device `powf` instead of `__powf` still failed). The launcher now computes `inv_freq = 1 / theta^(2i / head_dim)` on the host exactly as the naive launcher does and passes the table to the kernel by value (`head_dim` at most 256). All 9 `FastRope` tests pass. (Part C, fix by Claude)

- Parallelize `engine::fast::rope` over pairs and head groups: one block per token whose threads own a `(pair, head group)` slice, so `cosf` and `sinf` are computed once per pair and reused for the heads of that thread instead of once per head, and the 36 rotated heads of TinyLlama are split across 8 thread groups of 32 pairs (256 threads; the first draft used 128 threads of which 36 worked, each looping over all 32 pairs serially). New `engine::Sampler(max_rows)` (`include/engine/runtime/sampler.h`, `src/runtime/sampler.cpp`, in `engine_runtime`) owns the device array: `sampler(ids, logits, rows, stream)` checks there is one `SampleRow` per logits row and at most `max_rows`, validates every row's parameters on the host (the kernel trusts them), copies them up with `cudaMemcpyAsync` on the same stream and launches `sample`. `generate` now samples every step through a one-row `Sampler`, greedy included; its tests, including the free-running HF check, are unchanged. The sampler tests now go through `Sampler`; new ones: temperature 0 equals the greedy kernel on tie-heavy random rows whatever the seed and step, and in an 8-row batch mixing greedy and sampled rows with different seeds and steps each row draws the same token alone and in reversed batch order. Using the batch row as the subsequence, reading every row's parameters from row 0, ignoring the step, or perturbing the greedy rows each fails a test. (Part B)
- Add top-k sampling: `SamplingParams::top_k` (default 0, off; negative values are rejected by `validate`). After the temperature, as in HF (`TemperatureLogitsWarper`, then `TopKLogitsWarper`), only the tokens whose scaled logit `s_i = logit_i / temperature` is at least the k-th largest stay drawable, ties with the k-th value included, exactly HF's rule `scores < topk(scores, k)[-1]` (checked in transformers 5.17: `k = 2` on `[3, 2, 2, 2, 1, 0]` keeps all three 2s); the other tokens get `-inf` before the Gumbel-max argmax. There is no sort: each `s_i` maps to an order-preserving 32-bit key (the sign bit flipped for positives, all bits for negatives, `-0` folded into `+0` first so they tie as HF compares them), and the kernel binary-searches the largest key `K` with `count(key_i >= K) >= k` in 32 rounds, each a count over the row and a block-wide sum (warp `__shfl_xor_sync` butterflies plus one shared array, so every thread gets the same total and the loop stays uniform across the block). The noise of each token is unchanged, so `top_k = 0` or `top_k >= vocab` draws exactly what plain sampling draws, and greedy rows ignore `top_k`. Tests: chi-square against the truncated softmax on a 7-token row (k = 2, 4, 5 at temperatures 0.5 and 2) and on two HF logits rows (k = 10 at 0.7, k = 50 at 1), never drawing a cut token; ties at the k-th value all kept; all-negative rows and `-0` against `+0`; `top_k = 1` equals greedy; `top_k` of 0, 32,000, 32,001 and `INT32_MAX` equal plain sampling; `-inf` never drawn; a negative `top_k` rejected. Not folding `-0`, flipping only the sign bit for negatives, or keeping fewer than k each fails a test. (Part B)
- Add top-p (nucleus) sampling: `SamplingParams::top_p` (default 1, off; `validate` rejects anything outside (0, 1], NaN included). Applied after the temperature and top-k, as in HF, on the distribution renormalized over the tokens top-k kept: a token stays drawable when the probability of the tokens with a strictly larger scaled logit is below `p`, so the kept set is the smallest group of top tokens whose mass reaches `p`, and the top token always stays. The kernel finds that threshold without sorting: the row's maximum (a block-wide `fmaxf` reduction), then a binary search over the same 32-bit keys for the smallest key `K` with `mass(key > K) < p * mass(kept)`, where `mass` sums `expf(s - max)` in FP32 over the row (the max subtraction keeps logits near 100 from overflowing). `block_sum` became `block_reduce(v, op)` for both reductions. Ties at the cut stay together, the rule the build plan describes and HF's own top-k uses; HF's top-p instead keeps part of a tied group, chosen by `torch.sort`'s order among equal values. Probed against transformers 5.17 on the last prompt row of all 20 reference prompts (`T, k, p` of `1, 0, 0.9`, `1, 20, 0.8`, `1.5, 0, 0.95`, `1.2, 0, 0.7`): BF16 logits tie often (an ulp is 0.0625 near 10), so 9 of 20 rows at `p = 0.9` cut inside a tie group and we keep 1 to 3 more tokens than HF (up to 17 at `T = 1.5, p = 0.95`), always a superset whose extra tokens tie with HF's last kept one. On CUDA HF's choice is exactly "the higher index ranks first among equal values" (80 of 80), but on CPU the same call keeps other tokens of the group in 16 of 80 cases, so there is no single HF answer to copy. Tests: chi-square against the nucleus on a 7-token row (five settings, one combined with top-k) and on two HF rows (`p = 0.9`; `T = 1.5, p = 0.8`, which keeps 453 tokens on the unicode prompt; top-k 20 then `p = 0.8`), each asserting the setting is at least 1e-4 away from a cut so float rounding cannot flip it; `p` halfway between consecutive cumulative masses keeps exactly 1 to 6 planted top tokens; a tied group at the cut is kept whole; logits near 100 at temperatures 1 and 0.5; a tiny `p` equals greedy; `p = 1` equals plain sampling and `p = 0.5` does not; `-inf` never drawn; bad `p` rejected. Counting the crossing token's own mass, normalizing over the whole row instead of the top-k set, skipping top-p when top-k is on, ignoring top-k's threshold, or dropping the max subtraction each fails a test. (Part B)

Query head `h` reads KV head `h / (heads / kv_heads)`. One 256-thread block per (token, head) holds the query and one score per context position in dynamic shared memory (the launcher rejects contexts that do not fit in 48 KB, about 12,000 positions at `head_dim` 64; TinyLlama's limit is 2,048) and reproduces HF's eager BF16 arithmetic step by step: each score is an FP32 dot product rounded to BF16 and then scaled by `1 / sqrt(head_dim)` and rounded again (exact for 64); softmax in FP32 with `expf` and rounded to BF16, as `softmax(..., dtype=float32).to(bfloat16)` does; then the FP32 weighted sum of V rounded to BF16. The max and the sum are taken serially by one thread, which is slow but gives a fixed order. A CPU reference with the same roundings and the same `fma` order matches on four head layouts (including MHA and a single KV head) at up to 300 tokens except where CUDA's `expf` (up to 2 ulps off) and glibc's differ: that flips the BF16 rounding of a few probabilities, and cancellation in a weighted average of random values can turn one flip into hundreds of ulps of a small output. With correctly rounded `exp` on both sides the match was exact, so the test allows each element to be off by `2^-7 * (sum_j p_j |v_j| + |out|)`, the effect of every probability flipping by one ulp, on at most 0.1% of elements. Exact tests: decoding one token at a time after a 13-token prefill equals one 40-token prefill, a single token returns its own V head (which pins the GQA mapping), and garbage in cache rows past the query position does not change the result. Making every head read KV head `h % kv_heads`, dropping the causal limit, or skipping the probabilities' BF16 rounding each fails the tests. (Part B)
- Add `Attention.MatchesHuggingFaceAttnOnEveryTracedLayer`, the first check of RoPE and attention against HF: for each of the traced prompt's 22 layers it fuses the stored pre-RoPE `q`, `k` and `v` into one row per token, applies `naive::rope` at positions `0` to `T - 1`, stores K and V with `store_kv`, runs `naive::attention` and compares the result with `attn` (the `o_proj` input). It is not bit-identical: cuBLAS sums the QK and PV dot products in a different order than the kernel, so a score's BF16 rounding occasionally flips, and `exp` amplifies a flip in a large score. Measured on the 99-token prompt: 7 to 83 of 202,752 elements differ per layer (at most 0.04%), and the worst difference is 0.2% of the largest `|v|` in that column over the visible positions (the ulp counts look large, up to 28,414, only because some outputs are near zero). The test allows at most 0.1% of elements to differ, each by at most `2^-7` times that `|v|` maximum, a 4x margin. It fails on every layer when RoPE is skipped or `theta` is 1% off, and fails naming the layer when one `attn` element is changed by 64 ulps. (Part B)

## kernel/naive-oracles

- Add `engine::naive::embedding(out, ids, table, stream)` (`include/engine/kernels/embedding.h`), the first naive oracle kernel: one block per token copies that token's row of the BF16 `[vocab, hidden]` table into `out` `[T, hidden]` with a block-stride loop. The launcher checks dtypes and shapes and throws `std::invalid_argument` naming the operand, and returns without launching when `T` is 0 (a zero-size grid is an invalid launch). Ids are not range-checked on the device; they come from the tokenizer, which only produces valid ids. Shared pieces for the next kernels: `src/kernels/require.h` (the launchers' argument check) and, for tests, `tests/support/device.h` (`CudaStream`, `upload`, `download`), `tests/support/safetensors_file.h` (reads a named tensor from a mapped safetensors file), and `random_bf16`, `bf16_ulps` and `compare_bf16` in `tests/support/bf16.h` (mismatch count, worst distance in BF16 ulps and first index, so a failing comparison prints one line instead of two 100,000-element vectors). `Embedding.MatchesHuggingFaceOnEveryPrompt` reproduces HF's `embed` exactly on all 20 reference prompts and fails when one golden element is flipped by one bit. (Part B)
- Add `engine::naive::rmsnorm(out, x, weight, eps, stream)` (`include/engine/kernels/rmsnorm.h`): one 256-thread block per row sums the squares in FP32 (per-thread strided partial sums, then a shared-memory tree reduction), takes `rsqrtf(mean + eps)`, and writes `weight * bf16(x * rstd)` with HF's two roundings to BF16 (the normalized value is rounded before the weight multiply, as in `LlamaRMSNorm.forward`). `out` may alias `x`. The result is bit-identical to HF: `Rmsnorm.MatchesHuggingFaceLn1OnEveryTracedLayer` reproduces `ln1` of all 22 layers of the traced prompt (input `embed` or the previous layer's `out`) and `Rmsnorm.MatchesHuggingFaceFinalNormOnEveryPrompt` reproduces `final_norm` from layer 21's output on all 20 prompts, with zero mismatching elements; each fails, naming the layer or prompt, when one golden element is changed by one ulp. A CPU reference matches exactly on six shapes, including widths below and not divisible by the block size. `tests/support/reference.h` gains `reference_skip_reason()` and `traced_reference_prompt()`. (Part B)
- Let the RMSNorm tests allow rounding flips caused by FP32 summation order: at most 2 ulps on at most 0.1% of the elements (`close_up_to_reduction_order` in `tests/support/bf16.h`). The kernel's tree reduction adds the 2,048 squares in a different order than PyTorch's reduction kernel, so the sum, and therefore `rstd`, can differ in its last FP32 bits on rows that one large activation dominates; that occasionally flips the rounding of the normalized value by 1 ulp, which the weight multiply turns into at most 2 ulps. `ln1` and `final_norm` happen to match exactly, but `ln2` (next commit) differs on 12, 37 and 8 of 202,752 elements in layers 3, 5 and 13, and replaying the kernel's summation order in PyTorch reproduces exactly those counts. The bound still catches real errors: removing HF's intermediate rounding to BF16 changes about 26% of the elements, and a golden element changed by 256 ulps fails. (Part B)
- Add `engine::naive::add(out, a, b, stream)` (`include/engine/kernels/add.h`), the residual add: one thread per element computes `bf16(float(a) + float(b))`, which is what PyTorch does for BF16 tensors. Any shape, as long as `out`, `a` and `b` agree; `out` may alias `a` or `b`. `Add.RebuildsHuggingFaceLn2AndOutOnEveryTracedLayer` rebuilds each of the traced prompt's 22 layers from its traced pieces: `h = input + o`, then `rmsnorm(h)` against `ln2` (within the summation-order bound) and `h + down` against `out` (exactly, on every layer). It fails when one `out` element is changed by one ulp or one `ln2` element by 256. (Part B)
- Add `engine::naive::rope(qkv, positions, heads, kv_heads, theta, stream)` (`include/engine/kernels/rope.h`), rotary position embedding applied in place to the Q and K heads of a fused `[T, (heads + 2 * kv_heads) * head_dim]` row (the weight planner's Q, K, V order), leaving V untouched. It pairs element `i` with `i + head_dim / 2` like HF's `rotate_half` and reproduces HF's BF16 arithmetic: cos and sin computed in FP32 and rounded to BF16, then every product and the final sum rounded to BF16. The launcher computes `inv_freq = 1 / theta^(2i / head_dim)` on the host with `std::pow` on floats and passes it to the kernel by value (`head_dim` at most 256): HF computes `inv_freq` once on the CPU, and CUDA's `powf` differs from it in the last bit for 2 of TinyLlama's 32 frequencies, which at positions near 2,047 moved enough angles to change 57 of 1.4 million outputs by up to 64 ulps (the subtraction in `x * cos - y * sin` cancels, so a 1-ulp change in a rounded sine is many ulps of a small result). The host formula matches PyTorch's CPU values bit for bit at head dims 2, 8, 64 and 128. Checked once against HF's own `LlamaRotaryEmbedding` and `apply_rotary_pos_emb` on the traced prompt's pre-RoPE `q` and `k` of layers 0, 7 and 21 and on random inputs at 683 positions up to 2,047: zero mismatches (the reference stores no post-RoPE tensors, so that check is not in the repo; branch 12's attention test covers RoPE against `layers.0.attn`). The tests require exact agreement with a CPU reference at positions up to 2,047 for three head layouts, an untouched V, the identity at position 0, and reject bad widths, an odd or too-large head_dim and mismatched positions. (Part B)
- Add `engine::naive::swiglu(out, gate_up, stream)` (`include/engine/kernels/swiglu.h`): for the fused `[T, 2 * ff]` gate-then-up projection output (the weight planner's order), one thread per output element computes `bf16(bf16(silu(gate)) * up)` with `silu(g) = g / (1 + expf(-g))` in FP32, the formula and the two roundings PyTorch uses for `act_fn(gate_proj(x)) * up_proj(x)` in BF16. `Swiglu.MatchesHuggingFaceActOnEveryTracedLayer` rebuilds the fused input from the traced prompt's `gate` and `up` and reproduces `act` exactly on all 22 layers, and fails naming the layer when one golden element is changed by one ulp. A CPU reference matches exactly on five shapes, and a hand example pins which half is the gate. (Part B)
