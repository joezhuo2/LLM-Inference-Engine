# Changelog

Changes are grouped by branch, newest first, in the order the branches merge into `main`. Each entry is tagged with its part of the delegation: Part A and Part B entries are written by Claude and reviewed by Joe, and Part C entries are written by Joe.

## sampling/temperature

- Move the greedy kernel's block argmax into `src/sampling/argmax.cuh`: `block_argmax(vocab, score)` scans a strided slice of `score(i)` per thread and reduces the (value, index) pairs in shared memory with the same rule as before (larger value wins, the lower index on equal values, `-inf` everywhere gives 0), so the temperature sampler can reuse it with a different score. `greedy` now passes `score(i) = float(logits[row, i])`; its results and tests are unchanged. (Part B)
- Add `engine::sample(ids, logits, temperature, seed, step, stream)` (`include/engine/sampling/sample.h`, `src/sampling/sample.cu`), temperature sampling on the GPU with the Gumbel-max trick: for each row of BF16 `[T, vocab]` logits it writes `argmax_i(logits[i] / temperature + g_i)` with `g_i = -log(-log(u_i))` and `u_i` uniform in (0, 1), which draws exactly from `softmax(logits / temperature)` in one pass, with no exponentials, normalization or sort. The uniforms come from cuRAND's counter-based Philox4x32-10 (`curand_init(seed, row, step * vocab + i)`, header-only device API, no library to link), so the draw is a pure function of (seed, row, step, i): the same seed and step repeat exactly, and different rows, steps or seeds use disjoint parts of the stream. `u = (x + 0.5) / 2^32` for a 32-bit `x` never reaches 0 or 1, and both logs are taken in double: a first version built `u` from 24 bits in float, and the Gumbel tail it then truncated at 17.3 and quantized coarsely is exactly where the winning noise of a 32,000-token row lies (its maximum is around `log(32000) = 10.4`), which failed the chi-square test on HF's logits (71 against a critical 39). `-inf` logits are never drawn, a row of `-inf` gives 0, and the temperature must be positive and finite (greedy decoding stays `greedy`). Tests: chi-square goodness of fit against the softmax (critical value at p = 0.001, deterministic seeds) on a 7-token row at temperatures 0.25 to 2 (200,000 draws each, the masked token never drawn) and on the last prompt row of HF's stored logits of two reference prompts at temperatures 0.7, 1 and 1.5 (100,000 draws each, tokens expected fewer than 20 times pooled into one bucket); a temperature of 0.05 equals greedy when the top logit leads by 2 (more than the Gumbel range); repeating the call repeats the ids, and changing the step or the seed, or moving to another row, redraws nearly every row; bad arguments are rejected. Dropping the temperature, sampling `-log(u)` instead of a Gumbel, ignoring the step or using one stream for every row each fails the tests. (Part B)
- Replace `generate_greedy` with `engine::generate(runner, prompt, max_new_tokens, eos_id, sampling, on_token)` and `SamplingParams { temperature, seed }` (`include/engine/runtime/generate.h`): a temperature of 0, the default, decodes greedily exactly as before, and a positive one draws each token with `sample` at step `i` for the `i`-th generated token, so the whole answer is a function of the prompt, the temperature and the seed. A negative, infinite or NaN temperature throws before the prefill. New tests: at temperature 1 the same seed gives the same 32 tokens, another seed gives another answer, the sampled answer differs from greedy, and temperature 0 with any seed is greedy; bad temperatures are rejected. The free-running HF check and the other tests only change the function name. (Part B)
- Add `--temperature T` (default 0, greedy) and `--seed N` to `engine generate`. Without `--seed` a 64-bit seed is drawn from `std::random_device`, and whenever the temperature is positive the temperature and seed are printed on stderr, so any sampled answer can be repeated. Checked by hand in release: the same seed gives the same haiku twice, another seed another one, and sampling decodes at about 108 tokens/s, the same as greedy (the double-precision logs do not show). The README's Running section describes both flags. (Part A)

## model/forward

- Add `engine::greedy(ids, logits, stream)` (`include/engine/sampling/greedy.h`, `src/sampling/greedy.cu`, built into `engine_kernels`), greedy decoding on the GPU: for each row of BF16 `[T, vocab]` logits it writes the index of the largest value to I32 `ids` `[T]`. Ties go to the lowest index, as `torch.argmax` returns the first maximum, which HF's greedy `generate()` uses. One 1024-thread block per row: each thread scans a strided slice keeping its best (value, index), then a shared-memory tree reduction keeps the larger value or, on equal values, the smaller index. A row of `-inf` returns 0. Tests: it matches a CPU first-maximum argmax at vocab sizes 1 to 32,000 and on the stored HF logits of all 20 reference prompts, ties at indices in the same thread, different threads and the last thread all resolve to the lowest index, and it rejects bad dtypes and shapes. Breaking the tie rule fails the tests. (Part B)
- Add `engine::ModelRunner` (`include/engine/runtime/model_runner.h`), the batch-1 forward pass over the naive kernels and a contiguous KV cache. The constructor takes the config, the device weights, `max_tokens` (the most tokens one `forward` call takes) and `max_context` (the KV cache length, at most `max_positions`), and allocates everything up front: a 32 MiB cuBLAS workspace and `Blas` handle, one buffer per activation sized for `max_tokens` rows (hidden, normed, fused QKV, attention output, projection, fused gate and up, SwiGLU output, logits), the token ids and positions, and the K and V caches of all 22 layers (`[max_context, kv_heads * head_dim]` each, 46 MB at 2,048). `forward(ids, all_logits, hook)` appends `ids` at positions `length()` to `length() + T - 1`: embedding, then per layer RMSNorm, the fused QKV GEMM, RoPE, `store_kv`, attention, the output GEMM and the residual add in place, RMSNorm, the fused gate and up GEMM, SwiGLU, the down GEMM and the second residual add, then the final norm and `lm_head`. It returns BF16 logits for the last token (`[1, vocab]`) or for every new token (`[T, vocab]`), valid until the next call; `hook(layer, hidden)`, when given, sees each layer's output (HF's `layers.{i}.out`) before the next layer overwrites it. `reset()` starts a new sequence at position 0 (the cache is not cleared; attention never reads past the current position). Empty input, more than `max_tokens` tokens or overflowing `max_context` throw before anything changes. Against HF on the traced prompt (and, measured, on all 20 prompts) the result is close but not bit-identical: the Q, O, gate and up GEMMs match HF exactly, but K, V and down do not, because PyTorch runs `k_proj` and `v_proj` as separate 256-wide GEMMs and goes through cuBLASLt, so cuBLAS picks different algorithms and summation orders (against an FP64 product our K and V are slightly more accurate than HF's, HF's down slightly more accurate than ours). The relative L2 error of the hidden states is at most 0.35% after layer 0, about 1.5% from layer 7 on and 2.6% at layer 21; over all 20 prompts the teacher-forced argmax matches at 1,834 of 1,842 positions (99.57%) with a mean absolute logit error of 0.028. The tests bound layer 0 by 1% and every layer by 5% relative L2, require a mean absolute logit error under 0.05 and a 99% argmax match on the traced prompt, check that one-token decode steps after a prefill stay within the same bounds of a single full prefill (never bit-identical: a one-row GEMM uses another cuBLAS kernel; 3 argmax flips in 1,151 rows over all prompts), that `reset` reproduces the logits bit for bit, and that bad sizes throw. Reading `ln1` instead of `ln2` or not offsetting decode positions by `length()` fails the tests; RoPE's theta 1% off does not (at 139 tokens it changes the logits less than the GEMM order does) and is left to branch 12's per-layer attention test. Test support: `tests/support/model.h` (the real weights, uploaded once per test binary) and `tests/support/logits.h` (row argmax, mean absolute difference, relative L2). (Part B)
- Add `ForwardGolden.TeacherForcedMatchesHuggingFaceOnEveryPrompt` (`tests/gpu/test_forward_golden.cpp`), the C++ golden harness for M2's teacher-forced criteria: each of the 20 reference prompts (prompt plus HF's greedy continuation) goes through `ModelRunner` in one prefill with all logits; every layer's output must be within 5% relative L2 of `layers.{i}.out`, and over all 1,842 positions the argmax of our logits must equal the argmax of HF's stored full-pass logits at 99% or more, with a mean absolute logit error under 0.05 (averaged over every logit of every position, not per prompt: the 31-token `capital` prompt alone is at 0.054). It prints one line per prompt (argmax matches, mean error, worst layer) and the totals. Measured: 1,834 of 1,842 (99.57%), mean error 0.0285, worst layer 2.6% (layer 21 of `capital`). Scaling one golden `layers.12.out` by 1.1 fails naming the prompt and layer; adding 2 to one prompt's golden logits fails the mean error. Skips without the model or the reference. (Part A)
- Add `engine::generate_greedy(runner, prompt, max_new_tokens, eos_id, on_token)` (`include/engine/runtime/generate.h`): resets the runner, prefills the prompt, then repeatedly picks the next token with `greedy` on the last row of logits, copies that one id to the host, reports it to `on_token` and feeds it back as a one-token decode step, stopping after `max_new_tokens` tokens or after EOS (included in the result, as HF's `generate()` does). It throws before starting when `max_new_tokens` is not positive or the prompt plus `max_new_tokens - 1` fed-back tokens would not fit in the runner's context. `GenerateTest.FreeRunningGreedyMatchesHuggingFaceUpToNearTies` generates up to 64 tokens for each of the 20 reference prompts and compares them with HF's `generated_ids`: 15 of 20 are identical, and the other 5 first differ at a BF16 near-tie in HF's own stored logits for the two candidate tokens (0, 0, 1, 1 and 2 ulps apart; at 3 of the 5, HF's own full pass prefers our token, and at 2 HF's logits are an exact tie). M2's original bar, identical on 18 of 20, is out of reach in BF16 even for HF against itself: HF's full-pass argmax agrees with its own KV-cached `generate()` at every step on only 14 of 20 prompts. So the test requires every prompt to be identical or to first diverge where HF's logits for the two tokens are at most 2 BF16 ulps apart, and prints the identical count. Changing one of HF's generated ids to a token 33,305 ulps below the top fails naming the prompt and step. Other tests: the limit on new tokens, stopping after EOS (with the EOS id set to a token the model will produce), the callback seeing every token in order, and rejected limits. (Part B)
- Add `engine::TextStream` (`include/engine/tokenizer/text_stream.h`), incremental detokenization for streaming output: `push(token)` decodes the whole sequence so far and returns only the text not returned before. Decoding the whole sequence (rather than each token alone) keeps SentencePiece's spacing right, since a piece's leading `▁` becomes a space only after the first word. When the text ends in U+FFFD it returns nothing yet, because a character that byte-fallback tokens spell over several tokens (an emoji is four `<0xNN>` pieces) decodes as the replacement character until its last byte arrives. Quadratic in the length, which is negligible at 2,048 tokens. Tests: words appear as they arrive, an emoji's first three byte tokens emit nothing, and for all 5,028 cases of the tokenizer golden whose full decode does not end in U+FFFD, the concatenated pushes equal `decode` of the whole sequence. Removing the hold-back fails both of the last two tests. (Part A)
- Add `engine generate --model <dir> --prompt <text> [--system <text>] [--max-new-tokens N]` (default 256): renders the chat template, encodes it, uploads the weights, sizes a `ModelRunner` for the prompt (`max_tokens` = prompt length, context = prompt plus `N`, at most `max_positions`), runs `generate_greedy` and streams the answer through `TextStream` to stdout, then prints the prompt and generated token counts, the time to the first token and the decode rate to stderr. A prompt that fills the whole context is rejected with its token count. CPU-only builds register the command but fail with `generate needs a CUDA build`. On the RTX 5060 (release build) a haiku prompt gives readable text at about 111 tokens/s after about 490 ms to the first token (that time includes one-time costs of the first calls; not broken down yet). The README gains a Running section. (Part A)

## kernel/naive-attention

- Add `engine::naive::store_kv(k_cache, v_cache, qkv, start, stream)` (`include/engine/kernels/attention.h`), the write side of the contiguous KV cache that the naive attention reads: it copies the K and V slices of each fused `[T, (heads + 2 * kv_heads) * head_dim]` row (the weight planner's Q, K, V order, after RoPE) into rows `start` to `start + T - 1` of two BF16 caches `[S, kv_heads * head_dim]`, with one strided `cudaMemcpy2DAsync` per cache. The slice widths come from the shapes alone (K starts at `width - 2 * kv_width`), so no head counts are needed. It throws when the rows do not fit in the cache, `start` is negative, the caches disagree in shape or the qkv row is not wider than K plus V, and does nothing for `T = 0`. This is batch-1 and contiguous only; M3 replaces it with the paged `write_kv` (Part C). Tests check that only the target rows change and hold exactly K and V. (Part B)
- Add `engine::naive::attention(out, qkv, k_cache, v_cache, start, heads, kv_heads, stream)`, causal grouped-query attention for batch 1 over the contiguous cache: query `t` of the fused `[T, (heads + 2 * kv_heads) * head_dim]` input sits at position `start + t` and attends to cache rows `0` to `start + t`, so the same call covers prefill (`start = 0`, `T` tokens) and decode (`T = 1`); the caller stores the new K and V first with `store_kv`. Query head `h` reads KV head `h / (heads / kv_heads)`. One 256-thread block per (token, head) holds the query and one score per context position in dynamic shared memory (the launcher rejects contexts that do not fit in 48 KB, about 12,000 positions at `head_dim` 64; TinyLlama's limit is 2,048) and reproduces HF's eager BF16 arithmetic step by step: each score is an FP32 dot product rounded to BF16 and then scaled by `1 / sqrt(head_dim)` and rounded again (exact for 64); softmax in FP32 with `expf` and rounded to BF16, as `softmax(..., dtype=float32).to(bfloat16)` does; then the FP32 weighted sum of V rounded to BF16. The max and the sum are taken serially by one thread, which is slow but gives a fixed order. A CPU reference with the same roundings and the same `fma` order matches on four head layouts (including MHA and a single KV head) at up to 300 tokens except where CUDA's `expf` (up to 2 ulps off) and glibc's differ: that flips the BF16 rounding of a few probabilities, and cancellation in a weighted average of random values can turn one flip into hundreds of ulps of a small output. With correctly rounded `exp` on both sides the match was exact, so the test allows each element to be off by `2^-7 * (sum_j p_j |v_j| + |out|)`, the effect of every probability flipping by one ulp, on at most 0.1% of elements. Exact tests: decoding one token at a time after a 13-token prefill equals one 40-token prefill, a single token returns its own V head (which pins the GQA mapping), and garbage in cache rows past the query position does not change the result. Making every head read KV head `h % kv_heads`, dropping the causal limit, or skipping the probabilities' BF16 rounding each fails the tests. (Part B)
- Add `Attention.MatchesHuggingFaceAttnOnEveryTracedLayer`, the first check of RoPE and attention against HF: for each of the traced prompt's 22 layers it fuses the stored pre-RoPE `q`, `k` and `v` into one row per token, applies `naive::rope` at positions `0` to `T - 1`, stores K and V with `store_kv`, runs `naive::attention` and compares the result with `attn` (the `o_proj` input). It is not bit-identical: cuBLAS sums the QK and PV dot products in a different order than the kernel, so a score's BF16 rounding occasionally flips, and `exp` amplifies a flip in a large score. Measured on the 99-token prompt: 7 to 83 of 202,752 elements differ per layer (at most 0.04%), and the worst difference is 0.2% of the largest `|v|` in that column over the visible positions (the ulp counts look large, up to 28,414, only because some outputs are near zero). The test allows at most 0.1% of elements to differ, each by at most `2^-7` times that `|v|` maximum, a 4x margin. It fails on every layer when RoPE is skipped or `theta` is 1% off, and fails naming the layer when one `attn` element is changed by 64 ulps. (Part B)
- Pull the CUDA compile job's container from NVIDIA's registry (`nvcr.io/nvidia/cuda:13.3.1-devel-ubuntu24.04`) instead of Docker Hub. The same image is published on both, but GitHub's hosted runners pull from Docker Hub anonymously from shared IP addresses, so the job failed on this branch's PR with `toomanyrequests: You have reached your unauthenticated pull rate limit` before any code was built; nvcr.io does not apply that limit to anonymous pulls. (Part A)

## kernel/naive-oracles

- Add `engine::naive::embedding(out, ids, table, stream)` (`include/engine/kernels/embedding.h`), the first naive oracle kernel: one block per token copies that token's row of the BF16 `[vocab, hidden]` table into `out` `[T, hidden]` with a block-stride loop. The launcher checks dtypes and shapes and throws `std::invalid_argument` naming the operand, and returns without launching when `T` is 0 (a zero-size grid is an invalid launch). Ids are not range-checked on the device; they come from the tokenizer, which only produces valid ids. Shared pieces for the next kernels: `src/kernels/require.h` (the launchers' argument check) and, for tests, `tests/support/device.h` (`CudaStream`, `upload`, `download`), `tests/support/safetensors_file.h` (reads a named tensor from a mapped safetensors file), and `random_bf16`, `bf16_ulps` and `compare_bf16` in `tests/support/bf16.h` (mismatch count, worst distance in BF16 ulps and first index, so a failing comparison prints one line instead of two 100,000-element vectors). `Embedding.MatchesHuggingFaceOnEveryPrompt` reproduces HF's `embed` exactly on all 20 reference prompts and fails when one golden element is flipped by one bit. (Part B)
- Add `engine::naive::rmsnorm(out, x, weight, eps, stream)` (`include/engine/kernels/rmsnorm.h`): one 256-thread block per row sums the squares in FP32 (per-thread strided partial sums, then a shared-memory tree reduction), takes `rsqrtf(mean + eps)`, and writes `weight * bf16(x * rstd)` with HF's two roundings to BF16 (the normalized value is rounded before the weight multiply, as in `LlamaRMSNorm.forward`). `out` may alias `x`. The result is bit-identical to HF: `Rmsnorm.MatchesHuggingFaceLn1OnEveryTracedLayer` reproduces `ln1` of all 22 layers of the traced prompt (input `embed` or the previous layer's `out`) and `Rmsnorm.MatchesHuggingFaceFinalNormOnEveryPrompt` reproduces `final_norm` from layer 21's output on all 20 prompts, with zero mismatching elements; each fails, naming the layer or prompt, when one golden element is changed by one ulp. A CPU reference matches exactly on six shapes, including widths below and not divisible by the block size. `tests/support/reference.h` gains `reference_skip_reason()` and `traced_reference_prompt()`. (Part B)
- Let the RMSNorm tests allow rounding flips caused by FP32 summation order: at most 2 ulps on at most 0.1% of the elements (`close_up_to_reduction_order` in `tests/support/bf16.h`). The kernel's tree reduction adds the 2,048 squares in a different order than PyTorch's reduction kernel, so the sum, and therefore `rstd`, can differ in its last FP32 bits on rows that one large activation dominates; that occasionally flips the rounding of the normalized value by 1 ulp, which the weight multiply turns into at most 2 ulps. `ln1` and `final_norm` happen to match exactly, but `ln2` (next commit) differs on 12, 37 and 8 of 202,752 elements in layers 3, 5 and 13, and replaying the kernel's summation order in PyTorch reproduces exactly those counts. The bound still catches real errors: removing HF's intermediate rounding to BF16 changes about 26% of the elements, and a golden element changed by 256 ulps fails. (Part B)
- Add `engine::naive::add(out, a, b, stream)` (`include/engine/kernels/add.h`), the residual add: one thread per element computes `bf16(float(a) + float(b))`, which is what PyTorch does for BF16 tensors. Any shape, as long as `out`, `a` and `b` agree; `out` may alias `a` or `b`. `Add.RebuildsHuggingFaceLn2AndOutOnEveryTracedLayer` rebuilds each of the traced prompt's 22 layers from its traced pieces: `h = input + o`, then `rmsnorm(h)` against `ln2` (within the summation-order bound) and `h + down` against `out` (exactly, on every layer). It fails when one `out` element is changed by one ulp or one `ln2` element by 256. (Part B)
- Add `engine::naive::rope(qkv, positions, heads, kv_heads, theta, stream)` (`include/engine/kernels/rope.h`), rotary position embedding applied in place to the Q and K heads of a fused `[T, (heads + 2 * kv_heads) * head_dim]` row (the weight planner's Q, K, V order), leaving V untouched. It pairs element `i` with `i + head_dim / 2` like HF's `rotate_half` and reproduces HF's BF16 arithmetic: cos and sin computed in FP32 and rounded to BF16, then every product and the final sum rounded to BF16. The launcher computes `inv_freq = 1 / theta^(2i / head_dim)` on the host with `std::pow` on floats and passes it to the kernel by value (`head_dim` at most 256): HF computes `inv_freq` once on the CPU, and CUDA's `powf` differs from it in the last bit for 2 of TinyLlama's 32 frequencies, which at positions near 2,047 moved enough angles to change 57 of 1.4 million outputs by up to 64 ulps (the subtraction in `x * cos - y * sin` cancels, so a 1-ulp change in a rounded sine is many ulps of a small result). The host formula matches PyTorch's CPU values bit for bit at head dims 2, 8, 64 and 128. Checked once against HF's own `LlamaRotaryEmbedding` and `apply_rotary_pos_emb` on the traced prompt's pre-RoPE `q` and `k` of layers 0, 7 and 21 and on random inputs at 683 positions up to 2,047: zero mismatches (the reference stores no post-RoPE tensors, so that check is not in the repo; branch 12's attention test covers RoPE against `layers.0.attn`). The tests require exact agreement with a CPU reference at positions up to 2,047 for three head layouts, an untouched V, the identity at position 0, and reject bad widths, an odd or too-large head_dim and mismatched positions. (Part B)
- Add `engine::naive::swiglu(out, gate_up, stream)` (`include/engine/kernels/swiglu.h`): for the fused `[T, 2 * ff]` gate-then-up projection output (the weight planner's order), one thread per output element computes `bf16(bf16(silu(gate)) * up)` with `silu(g) = g / (1 + expf(-g))` in FP32, the formula and the two roundings PyTorch uses for `act_fn(gate_proj(x)) * up_proj(x)` in BF16. `Swiglu.MatchesHuggingFaceActOnEveryTracedLayer` rebuilds the fused input from the traced prompt's `gate` and `up` and reproduces `act` exactly on all 22 layers, and fails naming the layer when one golden element is changed by one ulp. A CPU reference matches exactly on five shapes, and a hand example pins which half is the gate. (Part B)

## tokenizer/sentencepiece

- Add the SentencePiece C++ library as `engine_sentencepiece`: an installed copy found through pkg-config (Ubuntu's `libsentencepiece-dev` and Homebrew ship a `sentencepiece.pc`, not a CMake package) is used first, and otherwise v0.2.1 is fetched (pinned by SHA-256, static, no tcmalloc, `EXCLUDE_FROM_ALL` so its command-line tools are not built). v0.2.1 is the newest release that bundles its own trimmed absl; v0.2.2 git-clones and builds all of abseil at configure time. CI installs `pkg-config` and `libsentencepiece-dev` (0.2.0) on Ubuntu and in the CUDA container; macOS fetches 0.2.1, because Homebrew's 0.2.2 headers need a separate abseil install. The warning flags are now added after the dependencies, so `-Wall -Wextra -Wpedantic` applies to the engine's own targets only and third-party code cannot fail the zero-warning build. (Part A)
- Add `engine::Tokenizer` (`include/engine/tokenizer/tokenizer.h`), a move-only wrapper over SentencePiece that loads `tokenizer.model` and reproduces HuggingFace's TinyLlama tokenizer (transformers 5.17, `legacy: false`) rather than raw SentencePiece, which differs on leading spaces and special tokens. `encode(text, add_bos)` splits the text on the literal special-token strings (`<unk>`, `<s>`, `</s>`) and emits their ids, adds the `▁` word prefix only to the text before the first special token and only when it does not already start with a space, and encodes every other segment with no prefix. SentencePiece always adds the prefix, so each segment is encoded as `"\n" + segment` and the first two ids (the prefix and the `<0x0A>` byte piece, which BPE never merges with its neighbours) are dropped; the constructor rejects a model where `"\n"` does not encode that way. `decode(ids)` skips BOS, EOS and UNK like `skip_special_tokens=True` and rejects out-of-range ids. A Python prototype of these rules matched HF on 20,029 fuzzed strings (encode) and 5,000 decodes; the unit tests pin HF's ids for plain text, leading spaces, special-token text, emoji and CJK, and skip without the model. The SentencePiece header stays out of the public header (forward declaration plus `std::unique_ptr`). The fetched `sentencepiece-static` target is now built (it is linked for the first time) and compiled with `-w`, because its own code trips GCC 13's `-Wstringop-overflow`. (Part A)
- Add `chat_prompt(messages, add_generation_prompt)` (`include/engine/tokenizer/chat.h`), TinyLlama's Zephyr-style chat template rendered exactly as transformers renders its Jinja template: each message becomes `<|role|>\n` + content + `</s>\n`, and the generation prompt `<|assistant|>\n` follows the last message (none when there are no messages). Roles other than system, user and assistant throw instead of being silently dropped as the template would. Encoding the result with `add_bos = false` gives the same ids as `apply_chat_template(..., tokenize=True)`, which adds no BOS; a test pins those 16 ids for a one-message conversation. (Part A)
- Add `scripts/tokenizer_golden.py --model <dir> --out tests/golden/tokenizer.json`, which records HuggingFace's ids (with BOS) and `skip_special_tokens` decode for 28 hand-written edge cases and 5,000 seeded random strings over an alphabet heavy in spaces, newlines, angle brackets, special-token text and multi-byte characters, and `TokenizerGolden.MatchesHuggingFace`, which requires `Tokenizer` to reproduce every one (reporting the first 10 mismatches). It passes on all 5,028 cases and fails, naming the text, when one golden id is changed. Skips without the model or the golden file. (Part A)
- Add `scripts/prompts.json`, the 20 fixed chat prompts of the M2 correctness criteria (short facts, code, arithmetic, lists, a story, translation with accents, emoji and non-Latin scripts, system prompts and one multi-turn conversation), and `scripts/dump_reference.py --model <dir> --out tests/golden/reference`, which runs HF TinyLlama in BF16 with eager attention, greedily generates up to 64 tokens per prompt, then runs one forward pass over prompt plus continuation and writes `<name>.safetensors` per prompt: `input_ids` (I32), `embed`, `layers.{i}.out` for all 22 layers, `final_norm` and BF16 `logits`, captured with forward hooks. HF's own `output_hidden_states` was not used because in transformers 5.17 its last entry is the final norm and layer 21's raw output is missing. One traced prompt (default the first) also gets every layer's `ln1`, `q`, `k`, `v` (before RoPE), `attn`, `o`, `ln2`, `gate`, `up`, `act` and `down`, for debugging the forward pass one operation at a time. `manifest.json` records versions, device, the tensor meanings, and per prompt the messages, lengths, generated ids and text. A full run takes about 75 s on the RTX 5060 and writes 409 MB.
