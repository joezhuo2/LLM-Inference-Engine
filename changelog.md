## kernel/flash-prefill-div32

- Do the two divisions of `flash_attention_prefill`'s cache path (`key / block_size`, `key % block_size`) in 32 bits instead of 64. The compiler then needs 96 registers per thread instead of 115, so 5 thread blocks fit on an SM instead of 4 and 130 on the GPU instead of 104, and the 128 blocks of a 256-row chunk run in one wave. A key index on that path is below the chunk's `cached_lens` entry, an `int32_t`, so nothing is cut off. Measured (release, RTX 5060 Laptop GPU, 2026-11-10, both kernels in one session): Nsight Compute, last 256-row chunk of a 2,048-token prompt 0.924 to 0.578 ms per launch and 24.7% to 39.4% of the warp places filled; Nsight Systems, attention of that prompt as 8 chunks 73.0 to 50.5 ms and in one step 37.8 to 36.1 ms; with no profiler, chunking it with a budget of 256 costs 14% instead of 24% (228.1 against 199.3 ms, median of 5). Budgets whose chunks are just over 130 blocks or exactly 104 are slower than before (272: 66.8 to 70.5 ms of attention, 208: 57.6 to 61.7). The 24 kernel tests and the paged runner tests pass unchanged. (Part C, written by Claude at Joe's request)

## runtime/flash-prefill-wiring

- Wire `flash_attention_prefill` into `PagedRunner` behind a switch (#103). `PagedBatch` gains `chunk_starts` and `cached_lens` (filled by `build_paged_batch` for whole-prompt prefill steps and by `build_chunked_batch` for chunks, empty for decode steps), with `decode_rows()` and `longest_decode_context()`. `PagedRunner::stage` checks them (chunks end at the last row, none empty, `cached_lens` equal to the position of the chunk's first row, at most `max_seqs` chunks) and copies them and one block table row per chunk after the per-token arrays, whose offsets do not move, so captured decode graphs are unchanged. With `set_flash_prefill(true)`, `run_staged` sends the decode rows to the v2 or split kernel (the split count now comes from the decode rows only) and the chunk rows to `flash_attention_prefill`; the default stays the per-row decode kernels for every row. `engine bench --prefill-attention paged|flash` selects it and the summary CSV records `prefill_attention`. Tests: chunk fields in `tests/unit/test_paged_batch.cpp`; in `tests/gpu/test_paged_runner.cpp` whole-prompt and budget-8 runs of four prompts give the same argmax and logits within 5% relative L2 with either kernel, and bad chunk descriptions are rejected. Measured with the kernel as merged in #185 (release, RTX 5060 Laptop GPU, 2026-11-10, single request, 3 runs): TTFT 1,646 against 1,468 ms at 2,048 prompt tokens, 127 against 120 ms at 512 and level at 128, so it is 12% slower than the path it replaces and stays off. (Part B)
- Move `test_flash_prefill.cpp` from `todo_gpu_tests` to `gpu_tests` (`tests/gpu/`) and delete the `todo_gpu_tests` target: all 24 tests pass against the kernel merged in #185, and no todo targets remain. (Part A)
- Rewrite `flash_attention_prefill_kernel` as the tiled kernel its spec asked for. One warp owns 16 query rows of one query head (4 warps, so 4 heads, per thread block; the grid is 16-row tiles by groups of 4 heads) and streams the keys past them 16 at a time: Q K^T through `mma.sync.aligned.m16n8k16` on the tensor cores (two 8-key halves, head_dim / 16 steps each, FP32 accumulators), each score rounded as before, a causal mask, an online softmax per row with the row maximum and sum reduced over the 4 lanes that share a row, the weights rounded to BF16, then P V through the same mma into FP32 accumulators that stay in registers (head_dim / 8 columns; the value columns are interleaved so each lane reads its 8 values of a key with contiguous loads). The Q tile is loaded once per chunk segment; keys and values come from the paged cache below `cached_lens` and from qkv above it, as zeros past the last row of the segment, so nothing outside the context is read. No shared memory, no barriers, nothing shared between warps. A tile that spans several chunks handles them one after another. The kernel is a template on head_dim (16 to 128 in steps of 16) so the fragments unroll into registers, and qkv and both caches must be 4-byte aligned. All 24 kernel tests pass unchanged, including bit-identity alone or in a batch and whatever follows a row. Measured (release, RTX 5060 Laptop GPU, 2026-11-10, single request, 3 runs): TTFT 224 against 1,471 ms with the per-row decode kernels at 2,048 prompt tokens, 92 against 393 at 1,024, 47 against 120 at 512 and 13 against 19 at 128. (Part C, written by Claude at Joe's request)
- Give `flash_attention_prefill` a fallback for GPUs older than sm_80, which have neither BF16 nor the m16n8k16 shape in `mma.sync` (the CI compile check builds for sm_75 and failed on it): below `__CUDA_ARCH__` 800 the same fragments are multiplied with warp shuffles and explicit fused multiply-adds, one product at a time, so the kernel is the same code around it and only slower. Checked on this GPU by forcing the fallback with `ENGINE_FLASH_EMULATE_MMA`: the 24 kernel tests and the two paged runner prefill tests pass; it has not run on an sm_75 card. (Part C, written by Claude at Joe's request)
- Make `flash_attention_prefill` the default prefill attention (`PagedRunner`, so `engine serve` too; `engine bench --prefill-attention paged` gives the per-row decode kernels) and rerun the prefill section: `scripts/prefill_ttft.py` gains an `engine, paged prefill` series, and `docs/results.md` records TTFT 1,507.9 to 203.1 ms at 2,048 prompt tokens against llama.cpp's 231.4 ms in the same session (ahead at every length; 0.088 to 0.099 ms per prompt token), a table of the three attention paths with the first kernel from `results/prefill/first_flash_kernel.csv`, a Kernels row, and that chunking a lone prompt with a budget of 256 now costs 25% at 2,048 tokens. `docs/profiling.md` gets "FlashAttention prefill" with the layout, what was not tried and what was not measured (no Nsight Compute run, no memcheck). "Under load" and the long-prompt stall were not rerun. (Part B, results Part A)

## sched/scheduler-impl

- Implement `engine::Scheduler` (`src/sched/scheduler.cpp`, Joe's Part C): it owns the `BlockManager` and three collections (a FIFO waiting queue, the running list and the finished list), and a step is `schedule()` followed by `update(tokens)`. `schedule()` admits waiting requests first come first served while the running count stays below `max_batch`, the blocks for the whole current length fit (`can_allocate`) and the step's prompt tokens stay within `max_prefill_tokens`, stopping at the first request that does not fit, and returns them as a prefill step. ## sampling/temperature

- Move the greedy kernel's block argmax into `src/sampling/argmax.cuh`: `block_argmax(vocab, score)` scans a strided slice of `score(i)` per thread and reduces the (value, index) pairs in shared memory with the same rule as before (larger value wins, the lower index on equal values, `-inf` everywhere gives 0), so the temperature sampler can reuse it with a different score. `greedy` now passes `score(i) = float(logits[row, i])`; its results and tests are unchanged. - Add `engine::sample(ids, logits, temperature, seed, step, stream)` (`include/engine/sampling/sample.h`, `src/sampling/sample.cu`), temperature sampling on the GPU with the Gumbel-max trick: for each row of BF16 `[T, vocab]` logits it writes `argmax_i(logits[i] / temperature + g_i)` with `g_i = -log(-log(u_i))` and `u_i` uniform in (0, 1), which draws exactly from `softmax(logits / temperature)` in one pass, with no exponentials, normalization or sort. The uniforms come from cuRAND's counter-based Philox4x32-10 (`curand_init(seed, row, step * vocab + i)`, header-only device API, no library to link), so the draw is a pure function of (seed, row, step, i): the same seed and step repeat exactly, and different rows, steps or seeds use disjoint parts of the stream. `u = (x + 0.5) / 2^32` for a 32-bit `x` never reaches 0 or 1, and both logs are taken in double: a first version built `u` from 24 bits in float, and the Gumbel tail it then truncated at 17.3 and quantized coarsely is exactly where the winning noise of a 32,000-token row lies (its maximum is around `log(32000) = 10.4`), which failed the chi-square test on HF's logits (71 against a critical 39). `-inf` logits are never drawn, a row of `-inf` gives 0, and the temperature must be positive and finite (greedy decoding stays `greedy`). Tests: chi-square goodness of fit against the softmax (critical value at p = 0.001, deterministic seeds) on a 7-token row at temperatures 0.25 to 2 (200,000 draws each, the masked token never drawn) and on the last prompt row of HF's stored logits of two reference prompts at temperatures 0.7, 1 and 1.5 (100,000 draws each, tokens expected fewer than 20 times pooled into one bucket); a temperature of 0.05 equals greedy when the top logit leads by 2 (more than the Gumbel range); repeating the call repeats the ids, and changing the step or the seed, or moving to another row, redraws nearly every row; bad arguments are rejected. Dropping the temperature, sampling `-log(u)` instead of a Gumbel, ignoring the step or using one stream for every row each fails the tests. (Part B)

- Add `engine::naive::rope(qkv, positions, heads, kv_heads, theta, stream)` (`include/engine/kernels/rope.h`), rotary position embedding applied in place to the Q and K heads of a fused `[T, (heads + 2 * kv_heads) * head_dim]` row (the weight planner's Q, K, V order), leaving V untouched. It pairs element `i` with `i + head_dim / 2` like HF's `rotate_half` and reproduces HF's BF16 arithmetic: cos and sin computed in FP32 and rounded to BF16, then every product and the final sum rounded to BF16. The launcher computes `inv_freq = 1 / theta^(2i / head_dim)` on the host with `std::pow` on floats and passes it to the kernel by value (`head_dim` at most 256): HF computes `inv_freq` once on the CPU, and CUDA's `powf` differs from it in the last bit for 2 of TinyLlama's 32 frequencies, which at positions near 2,047 moved enough angles to change 57 of 1.4 million outputs by up to 64 ulps (the subtraction in `x * cos - y * sin` cancels, so a 1-ulp change in a rounded sine is many ulps of a small result). The host formula matches PyTorch's CPU values bit for bit at head dims 2, 8, 64 and 128. Checked once against HF's own `LlamaRotaryEmbedding` and `apply_rotary_pos_emb` on the traced prompt's pre-RoPE `q` and `k` of layers 0, 7 and 21 and on random inputs at 683 positions up to 2,047: zero mismatches (the reference stores no post-RoPE tensors, so that check is not in the repo; branch 12's attention test covers RoPE against `layers.0.attn`). The tests require exact agreement with a CPU reference at positions up to 2,047 for three head layouts, an untouched V, the identity at position 0, and reject bad widths, an odd or too-large head_dim and mismatched positions. (Part B)
- Add `engine::naive::swiglu(out, gate_up, stream)` (`include/engine/kernels/swiglu.h`): for the fused `[T, 2 * ff]` gate-then-up projection output (the weight planner's order), one thread per output element computes `bf16(bf16(silu(gate)) * up)` with `silu(g) = g / (1 + expf(-g))` in FP32, the formula and the two roundings PyTorch uses for `act_fn(gate_proj(x)) * up_proj(x)` in BF16. `Swiglu.MatchesHuggingFaceActOnEveryTracedLayer` rebuilds the fused input from the traced prompt's `gate` and `up` and reproduces `act` exactly on all 22 layers, and fails naming the layer when one golden element is changed by one ulp. A CPU reference matches exactly on five shapes, and a hand example pins which half is the gate. (Part B)

- Add `engine::Tokenizer` (`include/engine/tokenizer/tokenizer.h`), a move-only wrapper over SentencePiece that loads `tokenizer.model` and reproduces HuggingFace's TinyLlama tokenizer (transformers 5.17, `legacy: false`) rather than raw SentencePiece, which differs on leading spaces and special tokens. `encode(text, add_bos)` splits the text on the literal special-token strings (`<unk>`, `<s>`, `</s>`) and emits their ids, adds the `▁` word prefix only to the text before the first special token and only when it does not already start with a space, and encodes every other segment with no prefix. SentencePiece always adds the prefix, so each segment is encoded as `"\n" + segment` and the first two ids (the prefix and the `<0x0A>` byte piece, which BPE never merges with its neighbours) are dropped; the constructor rejects a model where `"\n"` does not encode that way. `decode(ids)` skips BOS, EOS and UNK like `skip_special_tokens=True` and rejects out-of-range ids. A Python prototype of these rules matched HF on 20,029 fuzzed strings (encode) and 5,000 decodes; the unit tests pin HF's ids for plain text, leading spaces, special-token text, emoji and CJK, and skip without the model. The SentencePiece header stays out of the public header (forward declaration plus `std::unique_ptr`). The fetched `sentencepiece-static` target is now built (it is linked for the first time) and compiled with `-w`, because its own code trips GCC 13's `-Wstringop-overflow`. (Part A)
- Add `chat_prompt(messages, add_generation_prompt)` (`include/engine/tokenizer/chat.h`), TinyLlama's Zephyr-style chat template rendered exactly as transformers renders its Jinja template: each message becomes `<|role|>\n` + content + `</s>\n`, and the generation prompt `<|assistant|>\n` follows the last message (none when there are no messages). Roles other than system, user and assistant throw instead of being silently dropped as the template would. Encoding the result with `add_bos = false` gives the same ids as `apply_chat_template(..., tokenize=True)`, which adds no BOS; a test pins those 16 ids for a one-message conversation. (Part A)
- Add `scripts/tokenizer_golden.py --model <dir> --out tests/golden/tokenizer.json`, which records HuggingFace's ids (with BOS) and `skip_special_tokens` decode for 28 hand-written edge cases and 5,000 seeded random strings over an alphabet heavy in spaces, newlines, angle brackets, special-token text and multi-byte characters, and `TokenizerGolden.MatchesHuggingFace`, which requires `Tokenizer` to reproduce every one (reporting the first 10 mismatches). (Part A)
